# 01: График платежей по позиции

**What to build:** Пользователь открывает карточку материала на новой вкладке «Платежи» и ведёт график платежей позиции: добавляет строки с названием, суммой, условием оплаты, необязательным сроком и порядком; правит их, переставляет и удаляет. Срок показывается с той же пометкой просрочки, что у операций-услуг. Каждое действие попадает в журнал событий позиции. Плановый платёж нигде не считается оплатой: сумма графика — самостоятельная величина, из стоимости позиции не выводится.

Детали схемы, ограничений и политик — в `.scratch/material-payments/REPORT.md`, разделы 3, 4, 7.1; черновик DDL — в `.scratch/material-payments/migration-draft.sql` (раздел 1).

### Состояние живой БД (проверено запросами к Data API)

Черновик миграции **уже применён** к linked-проекту, и применён именно в том
виде, в котором он лежал в `.scratch/material-payments/migration-draft.sql`:
имена объектов совпадают дословно, включая `spec_item_payment_plans_created_by_fkey`
и `SPEC_ITEM_NOT_FOUND` из триггера `payment_plan_sync_scope()`. Проверено
поведением на живых данных:

| Что проверено | Как | Результат |
| --- | --- | --- |
| Колонки и их состав | `select` по всем 13 колонкам; лишних (`paid_at`, `kind`, `payment_plan_id`) нет | совпадает с проектом |
| Триггер `payment_plan_sync_scope` | вставка с чужой организацией и несуществующим проектом | оба поля перезаписаны из позиции; на несуществующую позицию `P0001: SPEC_ITEM_NOT_FOUND` |
| Триггер `updated_at` | `update` строки через паузу | `updated_at` сдвинулся |
| CHECK суммы и текстов | вставка `amount = 0`, `amount < 0`, `title = "   "`, `condition = "  "` | все отвергнуты `23514` с ожидаемыми именами ограничений |
| Уникальность порядка | дубль `(spec_item_id, position)`; тот же номер у другой позиции; тот же номер после soft-delete | `23505`; у другой позиции разрешён; после soft-delete место свободно |
| `NOT NULL`/FK | `project_id = NULL`, `created_by` с несуществующим пользователем | поле перезаписано триггером; FK `created_by` назван как в проекте |
| Доступ | `anon`: `select` и `insert` | `42501 permission denied` — таблица закрыта для `anon` |
| Виды событий | вставка пробы на каждый вид | все шесть `payment_*` принимаются CHECK-ом |
| Живой сценарий | события `payment_plan_added` / `payment_plan_changed` с автором Andy | записаны из интерфейса; payload дословно совпал с тем, что пишет код (`plan_id`, `title`, `amount`, `condition`, `due_date`, `position`, `changes[].field/from/to`) |

Осталось (без изменений):

1. **Миграция в репозитории приведена к живому состоянию**: список видов событий
   в ней — все шесть `payment_*` (иначе тест `history.test.ts` сверял бы код с
   файлом, а не с БД), и она стала идемпотентной: таблица, индексы, ограничения,
   политики и триггеры создаются только если их ещё нет, а CHECK видов событий
   переписывается лишь тогда, когда значения в нём нет. Повторный `db push` по
   журналу миграций ничего не сломает.
2. **Журнал миграций проекта.** Если черновик применялся через Dashboard, в
   `supabase_migrations.schema_migrations` записи о нём нет. `supabase migration
   repair --status applied 20261009` пометит его применённым **без** повторного
   выполнения; это безопаснее, чем `db push` вслепую. Проверить, что применено:
   `npx supabase migration list --linked` (нужно право `database_write`, у токена
   в `.env.local` его нет).
3. **Типы**: `npm run db:types` — сейчас `lib/supabase/database.types.ts`
   дополнен вручную ровно тем, что сгенерировал бы CLI для новой таблицы.
4. **Интеграционный тест не прогонялся**:
   `npx vitest run --config vitest.integration.config.mts`. Он требует применённой
   миграции — она применена, поэтому тест можно запускать как есть.
5. Три теста сервисных операций падают в этом окружении и к этой задаче не
   относятся: их модули (`service-operation-detail-cards`, `service-operation-modal`,
   `add-service-combobox`) не входят в граф изменённых файлов, а падение —
   расхождение разделителя разрядов (`40 000 ₽` против `40000 ₽`) в happy-dom.

### Ревью и что по нему исправлено

Ревью пройдено по двум осям (стандарты репозитория и соответствие тикету).
Исправлено:

- **перестановка** — шаг «увести в недостижимый диапазон» трогал ВЕСЬ график
  одним `-1` и обещал в шапке два UPDATE, делая N+1. Теперь трогаются только
  строки, у которых номер действительно меняется, у каждой свой отрицательный
  номер, а шапка объясняет, почему ограничение проверяется построчно и почему
  отказ второго шага оставляет график без дублей и повторяемым;
- **гонка двух добавлений** — при `23505` номер порядка пересчитывается и
  попытка повторяется ровно один раз (`lib/spec/payment-plan-mutations.race.test.ts`),
  вместо отказа «не удалось добавить платёж» на ровном месте;
- **`fmtRub`** в `lib/utils.ts` не возвращал `undefined` только по случайности:
  явный тип возврата `string` убрал работу в обход в сводке вкладки;
- `toAmount` больше не дублируется — экспортируется из `lib/spec/payment-schedule`;
- противоречия в комментариях (поля `position`, лимит условия оплаты, политика
  `DELETE` в миграции) и добавлен тест на главное правило этапа — сумма графика
  не зависит от стоимости позиции.

Осознанно оставлено:

- **машина состояний загрузки списка** во вкладке повторяет `files-tab.tsx`
  (loadedKey/inFlight/requestId) — вынесение в общий хук затронуло бы обе вкладки
  и не относится к этой задаче; кандидат на отдельную уборку;
- `paymentPlanCoverage` пока без продакшн-читателя: следующая задача (факты)
  показывает покрытие по строке графика (REPORT §7.1);
- вкладки «Платежи» в `?tab=` и в списке вкладок добавлены вместе — контракт
  вкладок один (`DETAIL_PANEL_TABS`).
