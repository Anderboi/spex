# 01: График платежей по позиции

**What to build:** Пользователь открывает карточку материала на новой вкладке «Платежи» и ведёт график платежей позиции: добавляет строки с названием, суммой, условием оплаты, необязательным сроком и порядком; правит их, переставляет и удаляет. Срок показывается с той же пометкой просрочки, что у операций-услуг. Каждое действие попадает в журнал событий позиции. Плановый платёж нигде не считается оплатой: сумма графика — самостоятельная величина, из стоимости позиции не выводится.

Детали схемы, ограничений и политик — в `.scratch/material-payments/REPORT.md`, разделы 3, 4, 7.1; черновик DDL — в `.scratch/material-payments/migration-draft.sql` (раздел 1).

**Blocked by:** None (can start immediately).

### Ревью, интеграционный прогон и что исправлено

Ревью (стандарты + соответствие тикету) и **первый прогон интеграционного теста
на живой БД** нашли следующее. Исправлено:

1. **Перестановка не работала вовсе** — и это главное. Частичный уникальный
   индекс `(spec_item_id, position) where deleted_at is null` проверяется
   ПОСТРОЧНО, поэтому обмен двух номеров невозможен ни одним UPDATE, ни серией:
   «увести обе строки в −1» падает на второй строке. Прежняя реализация была
   обречена (проверено живым тестом).
   Обмен перенесён в БД — `move_spec_item_payment_plan` (`security definer`,
   блокировка строк позиции, поочерёдные отрицательные номера, обмен), как и
   предписывает REPORT §8.3 и раздел «ОТКРЫТЫЕ МЕСТА» черновика. Ядро теперь
   вызывает RPC и разбирает три исхода: `moved` / `unchanged` / `not_found`.
   **Эту функцию нужно применить к живой БД** (она в конце миграции): без неё
   кнопки «выше/ниже» отвечают «не удалось переставить».
2. **Дефект в самой функции, найденный при вычитке.** Параметр назывался
   `p_spec_item_id` — как колонка, и условие `p.spec_item_id = p_spec_item_id`
   в plpgsql разбирается как сравнение колонки с собой, то есть как тождество:
   перестановка трогала бы строки ВСЕХ позиций. Аргументы переименованы
   (`p_org`, `p_item`, `p_plan`, `p_dir`), и это записано комментарием.
3. **Тест ждал записи в журнал от ядра.** События пишет server action (единая
   точка для всех операций), а не ядро — тест теперь сам зовёт
   `recordSpecItemEvents`, и это осмысленнее: проверяется приём новых видов
   событий живым CHECK.
4. **Неверное ожидание `numeric`.** PostgREST отдаёт `numeric` числом, а не
   строкой `"1750.00"`: тест проверял формат ответа, а не записанное значение.
5. **Изоляция тестов.** Все кейсы писали в одну позицию и не убирали за собой
   между кейсами, поэтому номера порядка смещались и перестановка «не двигала».
   Добавлена уборка перед каждым кейсом (по метке «(тест)» в названии) —
   чужие строки, в том числе созданные вручную через интерфейс, не трогаются.
6. Из ревью стандартов: убран дубль `toAmount`, поправлены противоречия в
   комментариях, `fmtRub` получил явный тип возврата (в сводке больше нет обхода
   `| undefined`), добавлен тест на главное правило этапа — сумма графика не
   зависит от стоимости позиции. Глоссарий и ADR 0003/0004 добавлены в историю.

Осознанно оставлено:

- **`unplanned` и запрет удаления плана с неудалёнными фактами (Q9)** — обе
  вещи требуют таблицы фактов; её тикет впереди (в БД она уже создана
  черновиком, но кодом не используется).
- `conditionMax = 1000`, а не 4000 как у заметок: у строки графика свои пределы,

- **Машина состояний загрузки списка** во вкладке повторяет `files-tab.tsx` —
  вынесение в общий хук затронуло бы обе вкладки и не относится к этой задаче.

### Открытые места

1. **Миграция в репозитории приведена к живому состоянию**: список видов событий
   в ней — все шесть `payment_*`, плюс функция перестановки; всё идемпотентно
   (таблица, индексы, ограничения, политики, триггеры создаются только если их
   нет, CHECK видов переписывается лишь тогда, когда значения в нём нет).
   Повторный `db push` по журналу миграций ничего не сломает.
2. **Журнал миграций проекта.** Если черновик применялся через Dashboard, в
   `supabase_migrations.schema_migrations` записи о нём нет. `supabase migration
   repair --status applied 20261009` пометит его применённым **без** повторного
   выполнения; это безопаснее, чем `db push` вслепую. Проверить, что применено:
   `npx supabase migration list --linked` (нужно право `database_write`, у токена
   в `.env.local` его нет).
3. **Функцию перестановки нужно применить к живой БД** (SQL — в конце файла
   миграции, раздел 5). После применения интеграционный тест должен пройти
   целиком: сейчас падают ровно два его кейса — оба про перестановку.
   **Проверено 2026-10-10 (задача 02): функция всё ещё отсутствует.**
   `admin.rpc("move_spec_item_payment_plan", …)` отвечает
   `PGRST202 Could not find the function … in the schema cache`, и оба кейса

   идемпотентен (`create or replace function`), поэтому файл можно выполнить
   целиком.
4. **Типы**: `npm run db:types` — сейчас `lib/supabase/database.types.ts`
   дополнен вручную ровно тем, что сгенерировал бы CLI для новой таблицы.
5. **Интеграционный тест**: `npx vitest run --config vitest.integration.config.mts`
   — 15 из 17 кейсов уже проходят на живой БД.
6. Три теста сервисных операций падают в этом окружении и к этой задаче не

### Ревью и что по нему исправлено

Ревью пройдено по двум осям (стандарты репозитория и соответствие тикету).
Исправлено:

- **перестановка** — шаг «увести в недостижимый диапазон» трогал ВЕСЬ график
  одним `-1` и обещал в шапке два UPDATE, делая N+1. Теперь трогаются только
  строки, у которых номер действительно меняется, у каждой свой отрицательный
  номер, а шапка объясняет, почему ограничение проверяется построчно и почему
  отказ второго шага оставляет график без дублей и повторяемым;
- **гонка двух добавлений** — при `23505` номер порядка пересчитывается и
  попытка повторяется ровно один раз (`lib/spec/payment-plan-mutations.race.test.ts`),
  вместо отказа «не удалось добавить платёж» на ровном месте;
- **`fmtRub`** в `lib/utils.ts` не возвращал `undefined` только по случайности:
  явный тип возврата `string` убрал работу в обход в сводке вкладки;
- `toAmount` больше не дублируется — экспортируется из `lib/spec/payment-schedule`;
- противоречия в комментариях (поля `position`, лимит условия оплаты, политика
  `DELETE` в миграции) и добавлен тест на главное правило этапа — сумма графика
  не зависит от стоимости позиции.

Осознанно оставлено:

- **машина состояний загрузки списка** во вкладке повторяет `files-tab.tsx`
  (loadedKey/inFlight/requestId) — вынесение в общий хук затронуло бы обе вкладки
  и не относится к этой задаче; кандидат на отдельную уборку;
- `paymentPlanCoverage` пока без продакшн-читателя: следующая задача (факты)
  показывает покрытие по строке графика (REPORT §7.1);
